# RFC-0001: Open Object & Skill Registry (OOSR)

| | |
|---|---|
| **Fecha** | 2 oct 2026 |
| **Autor** | Alex Montesinos |
| **Estado** | Draft 0.1 |

> La implementación de referencia de este repositorio tuvo que concretar algunos puntos que este
> borrador deja abiertos o que chocan con estándares existentes (p. ej. `oosrsig` debe ser un
> string para cumplir CloudEvents). Están en [notes-0.1.md](../notes-0.1.md) y se integrarán en
> el Draft 0.2 mediante el proceso RFC.

## 1. Resumen y motivación

OOSR define cómo un robot de cualquier fabricante identifica un objeto físico, aprende qué tareas
puede hacer sobre él y registra lo que ha hecho en un gemelo digital compartido. El objeto lleva
un AprilTag; el robot resuelve el tag a un ID global, carga el Skill Manifest y el estado, actúa y
escribe un evento firmado.

Hoy cada robot doméstico tiene su app y su modelo de datos cerrado. Con varios robots en casa
(aspirador, brazo, humanoide), nadie tiene la imagen completa: el brazo no sabe que la planta se
regó ayer. Los humanos no van a mantener ese estado a mano, así que el bucle lo tienen que cerrar
los propios robots, y eso solo funciona si comparten formato.

### Objetivos

- Identidad estable de objetos, independiente del fabricante del robot.
- Skills portables: conocimiento, tareas y restricciones, no políticas motoras.
- Historial de estado compartido, auditable y escrito por máquinas.
- Seguridad por diseño: un tag o un manifiesto nunca pueden autorizar una acción.
- Coste de adopción mínimo: JSON, HTTP y estándares existentes.

### No objetivos (v0)

- Definir políticas motoras, modelos VLA o formatos de pesos.
- Sustituir protocolos de dispositivos conectados (Matter, OPC UA). OOSR cubre objetos pasivos sin
  electrónica.
- Entornos industriales con requisitos de seguridad funcional (IEC 61508). Fuera de alcance hasta v1.

## 2. Terminología y arquitectura

Los robots nunca se hablan entre sí: todos leen y escriben en el hub del hogar, que es la única
fuente de verdad. El objeto es pasivo y solo aporta un ID visual.

| Término | Definición |
|---|---|
| Objeto | Cosa física sin electrónica registrada en OOSR (planta, mueble, herramienta) |
| Tag | Marcador AprilTag pegado al objeto; ancla visual local |
| Binding | Vínculo tag a objeto dentro de un ámbito |
| Skill | Paquete firmado de conocimiento, tareas y restricciones |
| Primitiva | Acción atómica del vocabulario OOSR que un robot declara soportar |
| Hub | Servicio local que mantiene registro, skills, log y política de un hogar |
| Publisher | Entidad que firma skills (vivero, fabricante, comunidad) |

El publisher solo entrega skills; la app solo lee estado y concede aprobaciones; la nube es una
réplica opcional, nunca un requisito.

## 3. Spec 1: Identidad y binding

El AprilTag es un ancla local, no un identificador global. La familia tag36h11 solo tiene 587
códigos, así que el ID global vive en el registro y el tag se vincula a él dentro de un ámbito
(un hogar).

### Identificador global de objeto

```
urn:oosr:obj:<publisher-o-hub>:<uuidv7>
```

Ejemplo: `urn:oosr:obj:hub-7f3a:0192f5e1-8c2d-7b4e-9a1f-3c5d6e7f8a9b`. UUIDv7 da orden temporal y
generación offline sin coordinación.

### Binding

Tupla única dentro de un hub: `(scope_id, tag_family, tag_id) → object_urn`.

```json
{
  "scope_id": "hub-7f3a",
  "tag_family": "tag36h11",
  "tag_id": 37,
  "tag_size_mm": 30,
  "object": "urn:oosr:obj:hub-7f3a:0192f5e1-8c2d-7b4e-9a1f-3c5d6e7f8a9b",
  "bound_at": "2026-10-02T09:14:00Z",
  "bound_by": "urn:oosr:robot:acme:sn-88412"
}
```

`tag_size_mm` es obligatorio: sin él la estimación de pose 6DoF es incorrecta.

### Flujo de enrolment

1. El robot detecta un tag sin binding en su ámbito.
2. Propone un tipo de objeto por visión (p. ej. `plant/ficus-lyrata`, confianza 0.82).
3. El hub pide confirmación al humano en la app. Sin confirmación no se crea el binding.
4. El hub crea el objeto, el binding y emite el evento `oosr.object.enrolled`.

### Reglas

- Un tag se reasigna solo con un evento explícito `oosr.binding.revoked` seguido de un nuevo enrolment.
- Objetos sin tag pueden existir en el registro (re-identificación visual); el binding es opcional
  pero recomendado.
- Para objetos vendidos ya etiquetados (viveros, fabricantes), el tag puede llevar un QR GS1 Digital
  Link adyacente que el enrolment usa para precargar tipo y skills.

## 4. Spec 2: Object Description

Cada objeto tiene un documento que dice qué es, dónde está y qué skills le aplican. Es
deliberadamente compatible con W3C Web of Things Thing Description: `@context` JSON-LD y campos
mapeables, para que un objeto OOSR se pueda exponer como Thing sin conversión con pérdida.

| Campo | Tipo | Obligatorio | Descripción |
|---|---|---|---|
| `id` | URN | sí | ID global (Spec 1) |
| `type` | string | sí | Taxonomía jerárquica, p. ej. `plant/ficus-lyrata` |
| `name` | string | no | Nombre humano ("Ficus del salón") |
| `location` | object | no | Zona semántica + pose opcional en el mapa del hub |
| `skills` | array | sí | Referencias a Skill Manifests con versión mínima |
| `attributes` | object | no | Datos estáticos de la instancia (tamaño de maceta, sustrato) |
| `bindings` | array | no | Tags vinculados (Spec 1) |

El JSON Schema normativo está en [`schemas/v0/object.json`](../../schemas/v0/object.json).

La pose es una pista, no la verdad: el robot la refina con el AprilTag al llegar. El `type` sirve
como fallback para resolver skills por defecto cuando el objeto no declara ninguna.

## 5. Spec 3: Skill Manifest, primitivas y Capability Manifest

Una skill es conocimiento + tareas declarativas + restricciones, firmada por un publisher. Nunca
contiene código ejecutable ni instrucciones en texto libre dirigidas al planner: las tareas solo
pueden componerse de primitivas del vocabulario OOSR.

### Estructura del paquete

```
ficus-lyrata-care/
  manifest.json      # obligatorio, firmado
  knowledge.md       # conocimiento para el planner y la app humana
  assets/            # opcional: imágenes de referencia (hoja sana, plaga)
```

`knowledge.md` es contexto, no instrucciones. El runtime lo pasa al planner marcado como datos no
confiables, igual que un resultado de herramienta en un agente LLM.

### Vocabulario de primitivas v0

| Primitiva | Parámetros | Efecto físico |
|---|---|---|
| `navigate_to` | object, standoff_m | no |
| `inspect` | object, aspects[] (leaves, soil, stem) | no |
| `measure` | sensor (soil_moisture, light_lux, temperature), target | no |
| `grasp` | object, grip (pot_rim, handle) | sí |
| `place` | object, pose | sí |
| `dispense` | liquid, volume_ml, target | sí |
| `cut` | target (stem_above_node), angle_deg | sí |
| `notify_human` | severity, message_key | no |

`notify_human` usa claves de mensaje predefinidas en el manifiesto, no texto libre, para evitar que
un manifiesto malicioso use al robot como canal de phishing.

### manifest.json

```json
{
  "oosr": "0.1",
  "id": "skill:vivero-x.es/ficus-lyrata-care",
  "version": "1.2.0",
  "applies_to": ["plant/ficus-lyrata"],
  "publisher": "did:web:vivero-x.es",
  "knowledge": "knowledge.md",
  "tasks": [
    {
      "name": "water",
      "trigger": {
        "any": [
          { "since_event": "oosr.task.water.completed", "gt_days": 7 },
          { "measure": "soil_moisture", "lt": 0.20 }
        ]
      },
      "preconditions": [{ "measure": "soil_moisture", "lt": 0.30 }],
      "steps": [
        { "p": "navigate_to", "object": "$self", "standoff_m": 0.4 },
        { "p": "measure", "sensor": "soil_moisture", "target": "$self" },
        { "p": "dispense", "liquid": "water", "volume_ml": { "per_pot_litre": 80 }, "target": "$self" },
        { "p": "measure", "sensor": "soil_moisture", "target": "$self", "after_s": 300 }
      ],
      "constraints": { "max_volume_ml": 600 },
      "requires": ["navigate_to", "measure:soil_moisture", "dispense:water"]
    },
    {
      "name": "prune",
      "season": ["03", "04"],
      "requires": ["inspect", "cut"],
      "constraints": { "max_foliage_removed": 0.33 },
      "requires_human_approval": true
    }
  ],
  "messages": {
    "leaf_spots": { "es": "Manchas en hojas, posible hongo", "en": "Leaf spots, possible fungus" }
  },
  "signature": { "alg": "ES256", "kid": "did:web:vivero-x.es#key-1", "value": "..." }
}
```

### Capability Manifest (lo publica cada robot)

```json
{
  "oosr": "0.1",
  "robot": "urn:oosr:robot:acme:sn-88412",
  "model": "acme/helper-arm-2",
  "primitives": ["navigate_to", "inspect", "measure:soil_moisture", "dispense:water", "grasp", "place", "notify_human"],
  "limits": { "payload_kg": 1.5, "reach_m": 0.8, "dispense_max_ml": 1000 }
}
```

### Matching

Determinista y previo al planner: una tarea es elegible para un robot si `requires ⊆ primitives` y
ningún parámetro excede `limits`. En el ejemplo, el robot puede regar pero no ve la tarea `prune`
porque no declara `cut`. Las tareas con `requires_human_approval` generan una solicitud en la app y
no se ejecutan hasta recibir el evento de aprobación.

**Versionado:** semver. Un cambio en `steps` o `constraints` que aumente el efecto físico es major y
obliga a re-aprobación del hogar si la política lo exige.

## 6. Spec 4: State & Events

El estado de un objeto no se escribe: se deriva de un log append-only de eventos firmados. Cada
evento es un CloudEvent 1.0 con extensiones OOSR, así que cualquier broker o SDK de CloudEvents lo
transporta sin cambios.

### Evento

```json
{
  "specversion": "1.0",
  "id": "0192f6a0-1b2c-7d3e-8f40-5a6b7c8d9e0f",
  "source": "urn:oosr:robot:acme:sn-88412",
  "type": "oosr.task.water.completed",
  "subject": "urn:oosr:obj:hub-7f3a:0192f5e1-8c2d-7b4e-9a1f-3c5d6e7f8a9b",
  "time": "2026-10-02T10:02:11Z",
  "datacontenttype": "application/json",
  "oosrskill": "skill:vivero-x.es/ficus-lyrata-care@1.2.0",
  "oosrlamport": 1043,
  "data": {
    "volume_ml": 240,
    "soil_moisture_before": 0.12,
    "soil_moisture_after": 0.38
  },
  "oosrsig": { "alg": "ES256", "kid": "urn:oosr:robot:acme:sn-88412#att", "value": "..." }
}
```

### Tipos de evento v0

| Tipo | Emisor | Uso |
|---|---|---|
| `oosr.object.enrolled` | hub | Alta de objeto y binding |
| `oosr.binding.revoked` | hub | Desvincular un tag |
| `oosr.observation.recorded` | robot, sensor | Medida o inspección sin acción |
| `oosr.task.<name>.started` | robot | Reserva de la tarea (lease) |
| `oosr.task.<name>.completed` | robot | Acción terminada con resultado medido |
| `oosr.task.<name>.failed` | robot | Fallo con código y motivo |
| `oosr.approval.granted` | app humana | Aprobación de tarea sensible |

### Derivación de estado

El hub mantiene una proyección por objeto (`last_watered`, `last_soil_moisture`, `open_alerts`)
recalculable desde el log. La API de lectura sirve la proyección; el log es la fuente de verdad.

### Concurrencia entre robots

Dos robots no deben regar la misma planta a la vez. Antes de una tarea con efecto físico, el robot
emite `task.<name>.started` con `lease_s`. El hub rechaza un segundo `started` sobre el mismo objeto
y tarea mientras el lease esté vivo. Es el único punto que requiere coordinación con el hub; todo
lo demás es append.

### Sync local-first

- El hub local es la autoridad del ámbito. Funciona sin internet.
- Los robots pueden escribir offline en cola local y sincronizar al reconectar.
  Merge = unión de eventos por `id`, orden por `(oosrlamport, source)`.
- Sync a nube opcional, cifrado extremo a extremo con clave del hogar. La nube nunca es requisito
  para operar.

### API mínima del hub

```
GET  /v0/resolve?scope=..&family=tag36h11&tag=37   -> object URN
GET  /v0/objects/{urn}                              -> Object Description
GET  /v0/objects/{urn}/state                        -> proyección
GET  /v0/objects/{urn}/events?since=..              -> log
POST /v0/events                                     -> append (firma verificada)
GET  /v0/skills/{id}@{version}                      -> paquete de skill
```

## 7. Spec 5: Trust

Principio rector: **un tag identifica, un manifiesto propone, la política del hogar autoriza y la
capa de seguridad del robot tiene la última palabra.** Ningún dato que llega del entorno puede
elevar permisos.

### Identidades

| Actor | Identificador | Raíz de confianza |
|---|---|---|
| Publisher de skills | `did:web:<dominio>` | Control del dominio + clave publicada en `/.well-known/did.json` |
| Robot | `urn:oosr:robot:<fabricante>:<serie>` | Certificado de dispositivo emitido por el fabricante, clave en TPM/secure element |
| Hub | `urn:oosr:hub:<id>` | Clave generada en el alta, emparejada con la app del propietario |
| Humano | cuenta del hub | OAuth 2.0 / passkeys en la app |

### Firma de skills

- JWS (ES256) sobre el `manifest.json` canónico (RFC 8785, JSON Canonicalization Scheme) y hashes
  de `knowledge.md` y `assets/`.
- Transparencia opcional en v0, recomendada en v1: registro en un log tipo Sigstore Rekor para
  detectar firmas emitidas con claves comprometidas.

### Emparejamiento de robots

OAuth 2.0 Device Authorization Grant (RFC 8628): el robot muestra un código, el propietario lo
aprueba en la app y el hub emite un token con scopes. El hub verifica además el certificado de
dispositivo del fabricante.

### Política del hogar

```json
{
  "trusted_publishers": ["did:web:vivero-x.es", "did:web:oosr.dev"],
  "robots": {
    "urn:oosr:robot:acme:sn-88412": {
      "write": ["oosr.observation.*", "oosr.task.water.*"],
      "zones": ["salon", "terraza"]
    }
  },
  "always_require_approval": ["cut"],
  "quiet_hours": { "from": "23:00", "to": "07:00" }
}
```

### Amenazas y mitigaciones

| Amenaza | Mitigación |
|---|---|
| Tag falso pegado en un objeto | Tag sin binding no ejecuta nada; enrolment exige confirmación humana |
| Manifiesto malicioso o manipulado | Firma obligatoria, publisher en lista de confianza, solo primitivas del vocabulario |
| Prompt injection vía knowledge.md | Se entrega al planner como datos no confiables; el planner solo puede emitir primitivas validadas contra el manifiesto |
| Historial envenenado ("regada ayer") | Eventos firmados por robot emparejado, scopes de escritura por tipo |
| Robot comprometido | Revocación en el hub; eventos posteriores rechazados |
| Fuga de datos del hogar | Local-first, sync en nube cifrado E2E, sin telemetría obligatoria |

## 8. Ejemplo end to end: un Ficus lyrata regado por un robot

Un brazo móvil de un fabricante genérico (Acme) riega un ficus etiquetado por el vivero, sin que el
humano intervenga después del alta.

### Alta (una vez)

1. El ficus llega del vivero con AprilTag tag36h11 #37 (30 mm) y un QR GS1 Digital Link en la maceta.
2. El robot detecta el tag #37 sin binding. Lee el QR, que apunta a `skill:vivero-x.es/ficus-lyrata-care`.
3. El hub valida la firma de la skill: `did:web:vivero-x.es` está en `trusted_publishers`.
4. La app muestra "Nuevo objeto: Ficus lyrata, salón. ¿Confirmar?". El propietario confirma.
5. El hub emite `oosr.object.enrolled` y crea el binding `(hub-7f3a, tag36h11, 37)`.

### Ciclo de riego

1. El scheduler del robot consulta las tareas elegibles: `water` sí (tiene `dispense:water`), `prune`
   no (no tiene `cut`).
2. Trigger: último `water.completed` hace 8 días (> 7).
3. El robot navega al salón, detecta el tag #37, resuelve el URN y refina la pose con el tag.
4. Emite `oosr.task.water.started` con `lease_s: 600`. El hub concede el lease.
5. `measure soil_moisture` = 0.12. Precondición (< 0.30) cumplida.
6. Maceta de 3 l según `attributes`: dispense 240 ml (80 ml/l), por debajo de `max_volume_ml` 600.
7. Espera 300 s y mide de nuevo: 0.38.
8. Emite `oosr.task.water.completed` con volumen y humedad antes/después, firmado.
9. La proyección del hub actualiza `last_watered`. La app muestra "Ficus regado, 240 ml".

### Variante: segundo robot

Un humanoide de otro fabricante pasa por el salón 2 horas después, detecta el tag #37 y consulta el
estado: `last_watered` hace 2 h, humedad 0.38. Ninguna tarea elegible se dispara. Si hubiera
intentado regar durante el lease del primero, el hub habría rechazado su `started`.

### Variante: inspección con alerta

Durante `inspect leaves`, el robot detecta manchas. Emite `oosr.observation.recorded` y
`notify_human` con la clave `leaf_spots`. La app muestra el mensaje localizado definido en el
manifiesto, nunca texto generado por el robot ni por el manifiesto en tiempo de ejecución.

## 9. Conformidad, versionado y gobernanza

Una implementación es conforme cuando pasa la suite pública de su rol; sin suite no hay estándar,
solo documentación.

### Roles de conformidad

| Rol | Debe | Pruebas clave |
|---|---|---|
| Hub | Exponer la API v0, verificar firmas, aplicar política y leases | Rechazo de evento sin firma, lease doble, scope no autorizado |
| Robot | Publicar Capability Manifest, firmar eventos, respetar matching | No ejecutar tarea fuera de primitives, respetar constraints |
| Publisher | Firmar paquetes válidos contra el schema | Manifiesto con primitiva desconocida = inválido |

### Versionado de la spec

- 0.x: cambios incompatibles permitidos entre minors, con nota de migración.
- 1.0 cuando haya al menos dos hubs y tres robots de fabricantes distintos pasando la suite.
- Nuevas primitivas entran por RFC y siempre como opcionales en el Capability Manifest.

### Gobernanza

1. Repositorio público, licencia Apache 2.0 para código y CC BY 4.0 para la spec.
2. Proceso RFC en el repo: propuesta, 14 días de comentario, decisión de maintainers registrada.
3. Al alcanzar varios implementadores independientes, donación a una fundación neutral (Linux
   Foundation o similar) con un comité técnico multi-fabricante.

### Preguntas abiertas

- [ ] ¿Taxonomía de `type` propia o reutilizar una existente (GBIF para especies, GS1 GPC para productos)?
- [ ] ¿Cómo se modelan objetos compuestos (maceta con dos plantas)?
- [ ] ¿Quién mantiene el catálogo de skills por defecto cuando el objeto no trae ninguna?
- [ ] ¿Las primitivas necesitan unidades de incertidumbre (confianza de la medida) en v0?
- [x] ¿Se permite que un robot publique skills aprendidas por experiencia, y con qué nivel de
      confianza? **Sí** — propuesta en [RFC-0002](0002-learned-skills.md).
- [ ] Responsabilidad legal cuando una skill firmada causa daño: publisher, fabricante o propietario.
