# RFC-0001: Open Object & Skill Registry (OOSR)

| | |
|---|---|
| **Author** | Alex Montesinos |
| **Status** | Draft 0.2 |
| **Created** | 2026-10-02 (Draft 0.1) |
| **Updated** | 2026-10-03 (Draft 0.2, see [Appendix A](#appendix-a-changes-since-draft-01)) |

The key words MUST, MUST NOT, SHOULD and MAY are to be interpreted as described in RFC 2119.
The JSON Schemas in [`schemas/v0`](../../schemas/v0) are normative; where this text and a schema
disagree, the schema wins and the text is a bug.

## 1. Summary and motivation

OOSR defines how a robot from any manufacturer identifies a physical object, learns which tasks it
can perform on it, and records what it did in a shared digital twin. The object carries an
AprilTag. The robot resolves the tag to a global ID, loads the Skill Manifest and the object's
state, acts, and writes a signed event.

Today every home robot ships its own app and closed data model. With several robots in a home
(vacuum, arm, humanoid), nobody has the full picture: the arm does not know the plant was watered
yesterday. People will not maintain that state by hand, so the robots themselves have to close the
loop, and that only works if they share a format.

### Goals

- Stable object identity, independent of the robot's manufacturer.
- Portable skills: knowledge, tasks and constraints, not motor policies.
- A shared, auditable, machine-written state history.
- Security by design: a tag or a manifest can never authorize an action.
- Minimal adoption cost: JSON, HTTP and existing standards.

### Non-goals (v0)

- Defining motor policies, VLA models or weight formats.
- Replacing protocols for connected devices (Matter, OPC UA). OOSR covers passive objects without
  electronics.
- Industrial environments with functional-safety requirements (IEC 61508). Out of scope until v1.

## 2. Terminology and architecture

Robots never talk to each other: they all read from and write to the home hub, which is the single
source of truth. The object is passive and only provides a visual ID.

| Term | Definition |
|---|---|
| Object | A physical thing without electronics registered in OOSR (plant, furniture, tool) |
| Tag | AprilTag marker attached to the object; a local visual anchor |
| Binding | Link between a tag and an object within a scope |
| Skill | Signed package of knowledge, tasks and constraints |
| Primitive | Atomic action from the OOSR vocabulary that a robot declares it supports |
| Hub | Local service holding a home's registry, skills, log and policy |
| Publisher | Entity that signs skills (nursery, manufacturer, community) |
| Manufacturer | Entity that certifies its robots' identity and keys |

The publisher only delivers skills; the app only reads state and grants approvals; the cloud is an
optional replica, never a requirement.

## 3. Spec 1: Identity and binding

An AprilTag is a local anchor, not a global identifier. The tag36h11 family has only 587 codes, so
the global ID lives in the registry and the tag is bound to it within a scope (a home).

### Global object identifier

```
urn:oosr:obj:<publisher-or-hub>:<uuidv7>
```

Example: `urn:oosr:obj:hub-7f3a:0192f5e1-8c2d-7b4e-9a1f-3c5d6e7f8a9b`. UUIDv7 gives temporal order
and offline generation without coordination.

### Binding

A unique tuple within a hub: `(scope_id, tag_family, tag_id) → object_urn`. Schema:
[`binding.json`](../../schemas/v0/binding.json).

```json
{
  "scope_id": "hub-7f3a",
  "tag_family": "tag36h11",
  "tag_id": 37,
  "tag_size_mm": 30,
  "object": "urn:oosr:obj:hub-7f3a:0192f5e1-8c2d-7b4e-9a1f-3c5d6e7f8a9b",
  "bound_at": "2026-10-02T09:14:00Z",
  "bound_by": "urn:oosr:robot:acme:sn-88412"
}
```

`tag_size_mm` is REQUIRED: without it, 6DoF pose estimation is wrong.

### Enrolment flow

1. A robot detects a tag with no binding in its scope.
2. It proposes an object type from vision (e.g. `plant/ficus-lyrata`, confidence 0.82), optionally
   with skill references read from an adjacent GS1 Digital Link QR code.
3. The hub asks the human to confirm in the app. **Without confirmation no binding is created.**
4. The hub creates the object and the binding and emits `oosr.object.enrolled`. If the proposal
   referenced skills from a trusted publisher that are not installed, the hub fetches them from the
   publisher's registry (§7) and verifies them; skills from untrusted publishers are never fetched.

### Rules

- A tag is reassigned only through an explicit `oosr.binding.revoked` event followed by a new
  enrolment.
- Objects without a tag MAY exist in the registry (visual re-identification); a binding is
  optional but recommended.
- For objects sold already tagged (nurseries, manufacturers), the tag MAY carry an adjacent GS1
  Digital Link QR code that enrolment uses to pre-fill type and skills. The QR code is a hint, never
  an authorization.

## 4. Spec 2: Object Description

Every object has a document stating what it is, where it is, and which skills apply to it. It is
deliberately compatible with the W3C Web of Things Thing Description: a JSON-LD `@context` and
mappable fields, so an OOSR object can be exposed as a Thing without lossy conversion. Schema:
[`object.json`](../../schemas/v0/object.json).

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | URN | yes | Global ID (Spec 1) |
| `type` | string | yes | Hierarchical taxonomy, e.g. `plant/ficus-lyrata` |
| `name` | string | no | Human name ("Living room ficus") |
| `location` | object | no | Semantic zone + optional pose in the hub's map |
| `skills` | array | yes | References to Skill Manifests with a minimum version |
| `attributes` | object | no | Static instance data (pot size, substrate) |
| `bindings` | array | no | Bound tags (Spec 1) |

The pose is a hint, not the truth: the robot refines it with the AprilTag on arrival.

### Standard attributes

Skills MAY rely on these instance attributes: `pot_volume_l` (litres) and `mass_kg`.

### Skill resolution

- If `skills` is non-empty, the hub uses, for each reference, the highest installed version with
  the same major as `min_version` and not lower than it. A new major version is never adopted
  automatically (§5, versioning).
- If `skills` is empty, `type` is the fallback: the hub uses the installed skills from trusted
  publishers whose `applies_to` matches most specifically. Matching is hierarchical by path prefix,
  so a skill for `plant` applies to `plant/ficus-lyrata`, but a skill for `plant/ficus-lyrata` wins.

## 5. Spec 3: Skill Manifest, primitives and Capability Manifest

A skill is knowledge + declarative tasks + constraints, signed by a publisher. It never contains
executable code or free-text instructions aimed at the planner: tasks can only be composed of
primitives from the OOSR vocabulary.

### Package layout

```
ficus-lyrata-care/
  manifest.json      # required, signed
  knowledge.md       # knowledge for the planner and for people
  assets/            # optional: reference images (healthy leaf, pest)
```

`knowledge.md` is context, not instructions. The runtime MUST pass it to the planner marked as
untrusted data, like a tool result in an LLM agent.

### Primitive vocabulary v0

| Primitive | Parameters | Physical effect | Qualifier |
|---|---|---|---|
| `navigate_to` | object, standoff_m | no | |
| `inspect` | object, aspects[] (leaves, soil, stem) | no | |
| `measure` | sensor (soil_moisture, light_lux, temperature), target | no | `sensor` |
| `grasp` | object, grip (pot_rim, handle) | yes | |
| `place` | object, pose | yes | |
| `dispense` | liquid, volume_ml, target | yes | `liquid` |
| `cut` | target (stem_above_node), angle_deg | yes | |
| `notify_human` | severity, message_key | no | |

Every step MAY carry `after_s` (wait before executing). `$self` refers to the object the skill is
applied to.

`notify_human` uses message keys predefined in the manifest, not free text, so a malicious manifest
cannot use the robot as a phishing channel.

### Capability strings and qualifiers

Robots declare, and tasks require, capability strings: a primitive optionally followed by its
qualifier, such as `measure:soil_moisture` or `dispense:water`. A qualifier names concrete
hardware (a soil probe, a water tank), so:

- a requirement `p` is satisfied by a robot declaring `p` or any `p:q`;
- a requirement `p:q` is satisfied only by a robot declaring `p:q`.

### Manifest

Schema: [`skill-manifest.json`](../../schemas/v0/skill-manifest.json).

```json
{
  "oosr": "0.1",
  "id": "skill:vivero-x.es/ficus-lyrata-care",
  "version": "1.2.0",
  "title": "Ficus lyrata care",
  "applies_to": ["plant/ficus-lyrata"],
  "publisher": "did:web:vivero-x.es",
  "knowledge": "knowledge.md",
  "integrity": { "knowledge.md": "sha256-3q2+7w..." },
  "tasks": [
    {
      "name": "water",
      "title_key": "task_water",
      "trigger": {
        "any": [
          { "since_event": "oosr.task.water.completed", "gt_days": 7 },
          { "measure": "soil_moisture", "lt": 0.20 }
        ]
      },
      "preconditions": [{ "measure": "soil_moisture", "lt": 0.30 }],
      "steps": [
        { "p": "navigate_to", "object": "$self", "standoff_m": 0.4 },
        { "p": "measure", "sensor": "soil_moisture", "target": "$self" },
        { "p": "dispense", "liquid": "water", "volume_ml": { "per_pot_litre": 80 }, "target": "$self" },
        { "p": "measure", "sensor": "soil_moisture", "target": "$self", "after_s": 300 }
      ],
      "constraints": { "max_volume_ml": 600 },
      "requires": ["navigate_to", "measure:soil_moisture", "dispense:water"]
    },
    {
      "name": "prune",
      "season": ["03", "04"],
      "requires": ["inspect", "cut"],
      "constraints": { "max_foliage_removed": 0.33 },
      "requires_human_approval": true
    }
  ],
  "messages": {
    "task_water": { "en": "Water", "es": "Regar" },
    "leaf_spots": { "en": "Leaf spots, possible fungus", "es": "Manchas en hojas, posible hongo" }
  },
  "signature": { "alg": "ES256", "kid": "did:web:vivero-x.es#key-1", "value": "eyJhbGciOiJFUzI1NiIs...<sig>" }
}
```

A task without `steps` MAY be composed by the planner, but only from the primitives in its
`requires`.

### Publisher rules (validated before signing and at install)

1. **Namespace.** The skill id MUST live in the publisher's namespace:
   `skill:<did:web method-specific id, with ':' replaced by '/'>/<name>`. `did:web:vivero-x.es`
   can only sign `skill:vivero-x.es/*`; `did:web:traxito.github.io:oosr` can only sign
   `skill:traxito.github.io/oosr/*`. Otherwise a trusted publisher could impersonate another
   publisher's skills.
2. Only primitives from the vocabulary. A manifest with an unknown primitive is invalid.
3. Every capability used by a step MUST be declared in `requires`.
4. Every `dispense` MUST be bounded: a numeric `volume_ml` or `constraints.max_volume_ml`. This keeps
   matching against robot limits decidable without knowing the object.
5. Every `message_key` and `title_key` MUST exist in `messages`.

### Conditions

`trigger` and `preconditions` use `any`, `all`, `since_event` and `measure` conditions, with
three-valued logic: an unknown measurement evaluates to *unknown*, not false. `since_event` with no
previous event counts as infinitely long ago. A robot SHOULD resolve unknowns with fresh,
non-physical measurements (`oosr.observation.recorded`) **before** reserving anything.

`season` lists months (`"01"`–`"12"`) written for the northern hemisphere. The household policy
declares `hemisphere` and `timezone`.

### Parameter resolution

`volume_ml` is either a number or `{ "per_pot_litre": n }`, resolved as `n × attributes.pot_volume_l`
and clamped to `constraints.max_volume_ml`. In the example, a 3 l pot gets 240 ml.

### Capability Manifest (published by each robot)

Schema: [`capability.json`](../../schemas/v0/capability.json).

```json
{
  "oosr": "0.1",
  "robot": "urn:oosr:robot:acme:sn-88412",
  "model": "acme/helper-arm-2",
  "primitives": ["navigate_to", "inspect", "measure:soil_moisture", "dispense:water", "grasp", "place", "notify_human"],
  "limits": { "payload_kg": 1.5, "reach_m": 0.8, "dispense_max_ml": 1000 }
}
```

### Matching

Deterministic, and done before any planner runs: a task is eligible for a robot if its required
capabilities (declared `requires` plus those used by `steps`) are satisfied by the robot's
`primitives`, and no parameter exceeds the robot's `limits` (`dispense` against
`dispense_max_ml`, `grasp` against `payload_kg` using `attributes.mass_kg`). In the example the robot
can water but does not see `prune`, because it does not declare `cut`.

The hub re-checks matching on every task event (§7). Robot-side matching is an optimization, not
the defense.

### Versioning

Semver. A change to `steps` or `constraints` that increases the physical effect is a major version
bump and requires re-approval by the household if its policy says so. The same version re-signed
(ECDSA signatures are randomized) is the same release; the same version with different content is
rejected.

## 6. Spec 4: State and events

An object's state is never written: it is derived from an append-only log of signed events. Each
event is a CloudEvent 1.0 with OOSR extensions, so any CloudEvents broker or SDK carries it
unchanged. Schema: [`event.json`](../../schemas/v0/event.json).

### Event

```json
{
  "specversion": "1.0",
  "id": "0192f6a0-1b2c-7d3e-8f40-5a6b7c8d9e0f",
  "source": "urn:oosr:robot:acme:sn-88412",
  "type": "oosr.task.water.completed",
  "subject": "urn:oosr:obj:hub-7f3a:0192f5e1-8c2d-7b4e-9a1f-3c5d6e7f8a9b",
  "time": "2026-10-02T10:02:11Z",
  "datacontenttype": "application/json",
  "oosrskill": "skill:vivero-x.es/ficus-lyrata-care@1.2.0",
  "oosrlamport": 1043,
  "data": {
    "volume_ml": 240,
    "soil_moisture_before": 0.12,
    "soil_moisture_after": 0.38
  },
  "oosrsig": "eyJhbGciOiJFUzI1NiIsImtpZCI6InVybjpvb3NyOnJvYm90OmFjbWU6c24tODg0MTIjYXR0In0..<sig>"
}
```

CloudEvents extension attributes MUST be scalar, so `oosrsig` is a string (§7, signatures).
`oosrskill` is REQUIRED on task events.

### Event types v0

| Type | Emitter | Use |
|---|---|---|
| `oosr.object.enrolled` | hub | Object and binding created (`data.object`, `data.binding`) |
| `oosr.object.updated` | hub | Name, zone, attributes or skills changed from the app (`data.changes`) |
| `oosr.binding.revoked` | hub | Tag unbound (`data.binding`) |
| `oosr.observation.recorded` | robot, sensor | Measurement or inspection without action |
| `oosr.task.<name>.started` | robot | Task reservation (lease) |
| `oosr.task.<name>.completed` | robot | Action finished, with measured result |
| `oosr.task.<name>.failed` | robot | Failure with `data.code` and reason |
| `oosr.approval.granted` | hub, on behalf of the owner | Approval of a sensitive task |
| `oosr.approval.denied` | hub, on behalf of the owner | Refusal of a sensitive task |
| `oosr.alert.acknowledged` | hub, on behalf of the owner | Alert handled (`data.message_key`) |

Robots MUST NOT emit hub event types.

### Data conventions

- Task results report measurements as `<sensor>_before` and `<sensor>_after`, plus effect fields
  such as `volume_ml` or `foliage_removed`.
- Observations report `data.measurements = { "<sensor>": value }`.
- `notify_human` is realized as `oosr.observation.recorded` with
  `data.notify = { "severity": ..., "message_key": ... }` and `oosrskill` set. The hub rejects keys
  not defined in that skill's `messages`. Apps show the localized string from the signed manifest,
  never text produced by the robot.

### State derivation

The hub keeps a per-object projection (`last_watered`, latest measurements, per-task last
started/completed/failed, `open_alerts`) recomputable from the log. The read API serves the
projection; the log is the source of truth.

### Concurrency between robots

Two robots must not water the same plant at once, nor water a pot that another robot is moving.
Before a task with physical effect, the robot emits `task.<name>.started` with `data.lease_s`
(1–3600, default 600).

- Tasks with physical effect share **one exclusive lease per object**. The hub rejects any physical
  `started` on that object while the lease is alive, including a second physical task by the robot
  that holds it.
- Tasks without physical effect lease per (object, task) and run alongside physical ones.
- The holder MAY renew its lease by emitting `started` again for the same task.
- A `completed` or `failed` for a physical task requires an open run started by the same robot,
  even if the lease expired, as long as nobody took it over.
- Leases expire by the hub's clock at reception, not the robot's.

This is the only point that requires coordination with the hub; everything else is append.

### Local-first sync

- The local hub is the authority for its scope. It works without internet.
- Robots MAY write offline to a local queue and sync on reconnection. Merge = union of events by
  `id`, ordered by `(oosrlamport, source)`. A robot SHOULD raise its Lamport clock to the hub's
  before writing. A robot without a connection cannot start physical tasks, because it cannot get
  a lease; observations can be queued.
- The hub rejects events whose `time` is more than 5 minutes in the future. Re-sending an identical
  event is idempotent; reusing an `id` with different content is a conflict.
- Optional cloud sync, end-to-end encrypted with a household key. The cloud is never required.

### Hub API v0

Read and write (robots and the app):


## 7. Spec 5: Trust

Guiding principle: **a tag identifies, a manifest proposes, the household policy authorizes, and
the robot's safety layer has the last word.** No data coming from the environment can escalate
permissions.

### Identities

| Actor | Identifier | Root of trust |
|---|---|---|
| Skill publisher | `did:web:<domain>` | Domain control + key published in its DID document |
| Manufacturer | `did:web:<domain>` | Same; certifies its robots (device certificates) |
| Robot | `urn:oosr:robot:<vendor>:<serial>` | Attestation key, ideally in a TPM or secure element, certified by the manufacturer |
| Hub | `urn:oosr:hub:<id>` | Key generated at setup, paired with the owner's app |
| Human | hub account | Owner credential in the app (OAuth 2.0 / passkeys planned; v0 uses an owner bearer token) |

### Signatures

All signatures are ES256 over the JCS (RFC 8785) canonical form of a JSON value.

- **Events:** `oosrsig` is a detached compact JWS (RFC 7515, Appendix F), `<header>..<signature>`,
  with header `{"alg":"ES256","kid":"<robot or hub>#<fragment>"}`, over the event without
  `oosrsig`. The `kid` MUST belong to the event `source`.
- **Skills:** `signature.value` is a detached compact JWS over the manifest without its `signature`
  member; `signature.alg` and `signature.kid` MUST match the JWS header, and the `kid` MUST belong
  to the `publisher`.
- **File integrity:** the manifest's `integrity` map lists `"sha256-<base64>"` for every other file
  in the package (SRI style) and is covered by the signature. A package with files not listed, or
  missing a listed file, is invalid.
- **Transparency:** optional in v0, recommended in v1: record signatures in a Sigstore Rekor-style
  log to detect signatures issued with compromised keys.

### Key resolution

The hub resolves `did:web` keys from the DID document's `assertionMethod`. To stay local-first, the
owner MAY pin keys (`POST /v0/trust/keys`); pinned keys are used before any network resolution.

### Skill registries

A publisher announces its registry with a DID service of type `OOSRSkillRegistry`:

```json
"service": [{ "id": "did:web:traxito.github.io:oosr#skills", "type": "OOSRSkillRegistry",
              "serviceEndpoint": "https://traxito.github.io/oosr/skills" }]
```

The registry serves `<endpoint>/index.json` (skills, versions, latest) and
`<endpoint>/<name>/<version>.json` (the package: manifest plus base64 files). Hubs install from a
registry only for publishers in `trusted_publishers`, and verify every package as in §5.

### Robot pairing

OAuth 2.0 Device Authorization Grant (RFC 8628): the robot shows a code, the owner approves it in
the app, and the hub issues a token whose write scopes come from the policy. At pairing the robot
presents its attestation public key; every event it signs is verified against that key.

### Device certificates

A device certificate is a compact JWS (typ `oosr-device+jwt`) signed by the manufacturer's
`did:web` key, with claims:

```json
{
  "iss": "did:web:acme.example",
  "sub": "urn:oosr:robot:acme:sn-88412",
  "model": "acme/helper-arm-2",
  "cnf": { "jwk": { "kty": "EC", "crv": "P-256", "x": "...", "y": "..." } },
  "key_storage": "tpm",
  "iat": 1791000000,
  "exp": 2106000000
}
```

`cnf` (RFC 7800) binds the robot's attestation key. The hub verifies, at pairing:

1. The robot URN's vendor segment maps to `iss` in the policy's `trusted_manufacturers`.
2. The signature, with a key that belongs to `iss`.
3. `sub` and `model` match the Capability Manifest, and `cnf.jwk` is the key the robot presents.
4. `iat` is not in the future and `exp`, if present, has not passed.

An invalid certificate always fails pairing. A missing certificate fails only if the policy sets
`require_device_cert`; otherwise the robot is paired as *unattested* and the app says so.
`key_storage` is the manufacturer's claim; proving it through hardware attestation is future work.

### Approvals

Tasks with `requires_human_approval`, or requiring a capability listed in the policy's
`always_require_approval` (primitives like `cut` or qualified capabilities like `dispense:water`),
need an approval:

1. The robot requests it (`POST /v0/approvals`) for an object, skill and task.
2. The owner grants or denies it in the app; the hub records `oosr.approval.granted` or
   `oosr.approval.denied`, signed with the hub's key on behalf of the owner.
3. The robot references it with `data.approval_id` in its `started`. An approval covers exactly
   (object, task, skill id, robot) and is single-use.

### Household policy

Schema: [`policy.json`](../../schemas/v0/policy.json).

```json
{
  "trusted_publishers": ["did:web:vivero-x.es", "did:web:traxito.github.io:oosr"],
  "trusted_manufacturers": { "acme": "did:web:acme.example" },
  "require_device_cert": false,
  "robots": {
    "urn:oosr:robot:acme:sn-88412": {
      "write": ["oosr.observation.*", "oosr.task.water.*"],
      "zones": ["living-room", "terrace"]
    }
  },
  "always_require_approval": ["cut"],
  "quiet_hours": { "from": "23:00", "to": "07:00" },
  "timezone": "Europe/Madrid",
  "hemisphere": "north"
}
```

### What the hub checks on every robot write

Schema, authenticated source, signature, duplicate id, clock skew, event type allowed for robots,
write scope, zone, skill installed and still trusted, skill applicable to the object, task exists,
robot eligible (matching), and for `started`: season, quiet hours (physical tasks), approval and
lease. Every refused write is recorded for audits (§9).

### Threats and mitigations

| Threat | Mitigation |
|---|---|
| Fake tag stuck on an object | An unbound tag executes nothing; enrolment requires human confirmation |
| Malicious or tampered manifest | Mandatory signature and integrity hashes, trusted publisher list, namespace bound to the publisher, vocabulary-only primitives |
| Prompt injection via knowledge.md | Passed to the planner as untrusted data; the planner can only emit primitives validated against the manifest |
| Poisoned history ("watered yesterday") | Events signed by a paired robot, per-type write scopes |
| Counterfeit or cloned robot | Device certificate binding URN, model and key to a trusted manufacturer |
| Compromised robot | Revocation in the hub; later events rejected; audit of refused writes |
| Phishing through the robot | `notify_human` only with message keys from signed manifests |
| Leak of household data | Local-first, end-to-end encrypted cloud sync, no mandatory telemetry |

## 8. End-to-end example: a Ficus lyrata watered by a robot

A mobile arm from a generic manufacturer (Acme) waters a ficus tagged by the nursery, with no human
involvement after enrolment. The reference implementation runs this scenario in its conformance
suite and in `npm run demo`.

### Enrolment (once)

1. The ficus arrives from the nursery with AprilTag tag36h11 #37 (30 mm) and a GS1 Digital Link QR
   code on the pot.
2. The robot detects tag #37 without a binding. It reads the QR code, which points to
   `skill:vivero-x.es/ficus-lyrata-care`.
3. The hub validates the skill's signature: `did:web:vivero-x.es` is in `trusted_publishers`.
4. The app shows "New object: Ficus lyrata, living room. Confirm?". The owner confirms.
5. The hub emits `oosr.object.enrolled` and creates the binding `(hub-7f3a, tag36h11, 37)`.

### Watering cycle

1. The robot's scheduler queries eligible tasks: `water` yes (it has `dispense:water`), `prune` no
   (it does not have `cut`).
2. Trigger: last `water.completed` 8 days ago (> 7).
3. The robot navigates to the living room, detects tag #37, resolves the URN and refines the pose
   with the tag.
4. It measures soil moisture: 0.12. The precondition (< 0.30) holds.
5. It emits `oosr.task.water.started` with `lease_s: 600`. The hub grants the lease.
6. 3 l pot according to `attributes`: it dispenses 240 ml (80 ml/l), below `max_volume_ml` 600.
7. It waits 300 s and measures again: 0.38.
8. It emits `oosr.task.water.completed` with volume and moisture before/after, signed.
9. The hub's projection updates `last_watered`. The app shows "Ficus watered, 240 ml".

### Variant: a second robot

A humanoid from another manufacturer passes through the living room 2 hours later, detects tag #37
and reads the state: `last_watered` 2 h ago, moisture 0.38. No eligible task triggers. Had it tried
to water during the first robot's lease, the hub would have rejected its `started`.

### Variant: inspection with an alert

During `inspect leaves`, the robot detects spots. It emits `oosr.observation.recorded` with
`notify` and the key `leaf_spots`. The app shows the localized message defined in the manifest,
never text generated by the robot or by the manifest at runtime.

## 9. Conformance, versioning and governance

An implementation is conformant when it passes the public suite for its role; without a suite there
is no standard, only documentation.

### Conformance roles

| Role | Must | Key tests |
|---|---|---|
| Hub | Expose API v0, verify signatures, enforce policy, leases and approvals | Unsigned event rejected, double lease, unauthorized scope, zone, approval, season, quiet hours, device certificates |
| Robot | Publish a Capability Manifest, sign events, respect matching and constraints | No task outside its primitives, results within constraints, well-formed runs, no writes the hub has to refuse |
| Publisher | Sign packages valid against the schema | Manifest with an unknown primitive is invalid; namespace bound to the publisher |

### Running the suite

- **Hub role:** `npm run conformance -- --url <hub> --token <owner token>` runs the suite against
  any hub over HTTP. It configures its test publisher and manufacturer through the API and restores
  the owner's policy when it finishes.
- **Robot role:** run the robot against a reference hub through a scenario, then
  `oosr-hub audit --robot <urn>` (or `GET /v0/robots/{urn}/audit`). The audit replays what the robot
  wrote, and what the hub refused, against its Capability Manifest and the skills it used.
- **Publisher role:** `oosr skill validate` and `oosr skill verify`.

### Spec versioning

- 0.x: incompatible changes allowed between minors, with a migration note.
- 1.0 when at least two hubs and three robots from different manufacturers pass the suite.
- New primitives enter by RFC, always as optional capabilities in the Capability Manifest.

### Governance

1. Public repository, Apache 2.0 for code and CC BY 4.0 for the spec.
2. RFC process in the repository: proposal, 14-day comment period, decision recorded by the
   maintainers.
3. Once there are several independent implementers, donation to a neutral foundation (Linux
   Foundation or similar) with a multi-vendor technical committee.

## Appendix A: Changes since Draft 0.1

Draft 0.1 (2026-10-02) was written in Spanish. Draft 0.2 is the first English version and the
normative text from now on. Changes, all found while building the reference implementation:

1. `oosrsig` is a detached compact JWS **string**, not an object: CloudEvents extension attributes
   must be scalar ([#7](https://github.com/traxito/oosr/issues/7)). Skill signatures use the same
   format inside `signature.value`.
2. New manifest field `integrity` (SRI hashes of package files), covered by the signature.
3. Skill ids are bound to the publisher's `did:web` namespace.
4. Publishers announce registries with an `OOSRSkillRegistry` DID service; hubs MAY pin keys.
5. Capability qualifiers (`measure:<sensor>`, `dispense:<liquid>`) and their matching rule.
6. Publisher rules: steps declared in `requires`, bounded `dispense`, defined message keys.
7. Standard attributes `pot_volume_l` and `mass_kg`; `volume_ml.per_pot_litre` resolution.
8. Three-valued conditions; `since_event` without a previous event is infinitely old. Robots
   measure before reserving, so the §8 example now measures before emitting `started`.
9. Policy fields `timezone` and `hemisphere`; seasons are written for the northern hemisphere.
10. Skill version selection by `min_version` within the same major.
11. New hub event types `oosr.object.updated`, `oosr.approval.denied`, `oosr.alert.acknowledged`;
    approvals are emitted by the hub on behalf of the owner.
12. `notify_human` realized as `oosr.observation.recorded` with `data.notify`.
13. Data conventions for measurements and results.
14. Physical tasks share one exclusive lease per object ([#8](https://github.com/traxito/oosr/issues/8));
    renewal, run ownership and hub-clock expiry are specified.
15. Log hygiene: future timestamps, idempotent re-sends, id conflicts.
16. Approval flow (request, decision, single use) and `always_require_approval` on capabilities.
17. Device certificates and policy fields `trusted_manufacturers`, `require_device_cert`
    ([#9](https://github.com/traxito/oosr/issues/9)).
18. Full hub API v0, including pairing, enrolment, approvals, trust keys and audit.
19. Conformance can run against any hub over HTTP; robot-role conformance via audit
    ([#11](https://github.com/traxito/oosr/issues/11)).
